# Phase D, measured: the input problem has one working answer, and the roadmap does not list it

**28 July 2026. Research, repo-only. Nothing here is served, deployed, or on chain. Nothing touches
`src/engine/`, so `q1-e1fa99d08887d6cc` does not move** (read out of `proof.js` at the time of
writing, not recalled).

The roadmap states Phase D as three approaches, in order of expected cheapness: signed venue data,
TEE attestation, zkTLS. All three were measured against the sources Quiver actually reads. Two of the
three are worse than the roadmap implies. The one that works is a fourth approach the roadmap does
not mention: **for the two venues that are themselves blockchains, the exact inputs Quiver consumes
are readable from the venue's own consensus state, and a contract can read them.**

I built the gate for it. It passes, and both halves work: it accepts honest inputs and refuses
fabricated ones.

---

## Four things measurement contradicts in the roadmap's own framing

**1. "Thirteen services read live markets" is off by one.** Thirteen services always ship an
observation envelope, but `macro-sentry` contacts nothing. `grep -c "fetch(\|adapters/"
engine/macroSentry.js` returns 0; it is a curated static calendar filtered against wall-clock `now`.
It is an observation because time moved, not because a venue was read. Twelve services read live
markets unconditionally; `perp-gate` and `portfolio-gate` read them conditionally, so **fourteen
services can contact an external host** and twelve always do.

**2. The abandon condition measures the wrong baseline.** It says abandon if no mechanism "gets below
the cost of simply re-fetching from the venue yourself". Re-fetching costs 180 to 590 ms and zero
money, so nothing beats it, and by that test Phase D is dead on arrival. But a re-fetch now does not
audit an observation made earlier, which is the actual claim an observation envelope makes. Measured
on the Hyperliquid mark: after 62 s a re-fetch differs from the committed value by up to 6.6e-4
relative, after 183 s by up to 5.9e-4. Ordinary drift exceeds any useful attestation bound inside a
minute. "Go look yourself" is a concurrent check, not an audit, and the abandon condition should say
so or it will retire the phase for the wrong reason.

**3. The OKX TEE claim is not supportable as written.** The roadmap says TEE attestation "is the
approach OKX's own wallet infrastructure uses for key custody, so it is not exotic in this
ecosystem". OKX's Onchain OS docs do state that Agentic Wallet keys are generated, stored and signed
inside a TEE. But OKX names no TEE technology, publishes no attestation format, no measurements, no
verifier, and no endpoint; the word attestation does not appear. Separately, OKX's retail Keyless
Wallet is documented as 2-of-3 MPC shares with no TEE claim at all. And the analogy runs the wrong
way regardless: key custody hides a secret inside a TEE, attested computation proves a result to a
third party. Forging one attestation breaks the second and not the first, which is exactly the
capability the sub-$1000 and sub-$50 physical attacks in §3.2 deliver. The sentence should be cut or
rewritten.

**4. The missing option is the one that works.** Neither the roadmap nor the whitepaper mentions
venue consensus state, light-client proofs, or `eth_getProof`. Two of Quiver's live sources are
blockchains and a third class of its inputs is chain state already. That is where the only
non-theatrical answer lives.

## 2. Do the venues sign anything? Measured, not assumed

`probe-sig.mjs` fetched fifteen endpoints, captured every response header, and scanned the JSON body
recursively for any key matching `sign|signature|proof|attest|pubkey|certificate|merkle|ecdsa|
ed25519|secp|digest|hmac|seal`.

| source | status | signature headers | signature fields in body |
|---|---|---|---|
| Hyperliquid `/info` | 200 | none | **none** |
| dYdX v4 indexer | 200 | none | **none** (one false positive: a token ticker literally named `SIGN-USD`) |
| Deribit public API | 200 | none | **none** |
| DefiLlama | 200 | none | **none** |
| Polymarket gamma | 200 | none | **none** |
| OKX v5 market | 200 | none | **none** |
| Coinbase spot | 200 | none | **none** |
| Binance ticker | 200 | none | **none** |
| Kraken ticker | 200 | none | **none** |
| Ethereum public RPC | 200 | none | **none** |
| **RedStone gateway** | 200 | none | **`signature`, `signerAddress`, `isSignatureValid`, five distinct signers per feed** |
| **Pyth Hermes** | 200 | none | **`binary.data`, 1,311 bytes, magic `PNAU`**, a guardian-signed accumulator update |
| Coinbase `/oracle` | **401** | n/a | route still mounted, auth-gated |

**Zero of the ten venues Quiver reads sign their response data.** The two networks that do sign are
oracle networks, not venues, and neither publishes the quantities Quiver needs (§3.3).

Two dates are worth recording because they explain why this gap is not an oversight. Coinbase
deprecated its signed Price Oracle on 2025-01-01; OKX took its Compound-compatible `Get oracle`
endpoint offline on 2025-01-07. Six days apart. Signed market data over HTTP existed and was
deliberately retired. The probe confirms the current state: Coinbase's route returns 401 rather than
404, so it exists and is gated; OKX's returns 404 while its auth-gated routes return `50103`, which
is the discriminating control showing it was removed rather than gated.

The direction of signing is uniformly backwards across the industry. Binance, Kraken, OKX, Coinbase,
Deribit and Polymarket all run mature signing infrastructure, and every bit of it points at inbound
requests. Deribit's response envelope is exhaustively `jsonrpc / id / result / testnet / usIn / usOut
/ usDiff`; there is no field a signature could occupy. Polymarket's `/book` carries a `hash`, which
is the trap case: it looks cryptographic, has no signer, and binds the data only to itself.

## 3. The survey

### 3.1 Signed venue data

**Does not exist for any source Quiver reads.** Measured above. Not partial, not awkward: zero.

The roadmap calls this "cheap, partial, honest" and puts it first because it might be enough. It is
not available at all. That is a stronger negative than the roadmap anticipated and it should be
written down as settled rather than left as a hopeful first option.

### 3.2 TEE attestation

**What it proves.** A measurement of the image that booted, plus up to 1,024 bytes of application
data the code itself chose to place in `user_data` (Nitro; 64 bytes on TDX/SGX). If TLS terminates
inside the enclave, the untrusted host proxying packets sees ciphertext only. AWS's KMS design is the
architectural proof they treat the parent as hostile: KMS returns ciphertext encrypted to the
attestation document's `public_key` rather than plaintext.

**What it does not prove, and this must be said in the same breath.** No TEE attests an HTTPS fetch.
"This blob is `SHA256(url ‖ response)`" is a convention your code implements, believed only by a
verifier who read the source behind the measurement and reproduced the build. The parent can still
drop, delay, reorder or replay packets, and can kill the enclave. It sees destination IPs, timing and
sizes. And the attestation says nothing about whether the venue told the truth.

**The security posture is worse than "the history of side-channel breaks is not short" conveys.**
Two attacks extract or forge attestation, which is categorically worse than leaking data, because
forging one attestation lets an attacker prove code ran in a TEE when it never did:

- **WireTap** (CCS '25): a DRAM interposer against 3rd-gen Xeon Scalable with DDR4 extracts the SGX
  attestation key. Cost "under $1000, including the logic analyzer." Intel's position is that this is
  outside the threat model and there are no mitigations besides physical security.
- **Battering RAM** (embargo lifted Sep 2025): a sub-$50 interposer, invisible at boot, that fully
  breaks SGX and breaks SEV-SNP attestation by replaying measurements, **on fully patched systems**.
  Both vendors say physical attacks are out of scope. No software fix is possible.

Server SGX shipped without the memory-integrity protection client SGX had, which is why these land
now. Intel discontinued SGX on client CPUs around 2022. Azure's confidential-computing portfolio page
(updated 2026-06-19) no longer lists SGX VMs at all, though the DCsv3 SKU still exists; GCP and AWS
never offered SGX.

**Cost, applicability and the on-chain problem.** Nitro's attestation is ECDSA over **P-384**. There
is no P-384 precompile on any EVM chain, and EIP-7951's `P256VERIFY` does not help because P-256 is
not P-384. Marlin got Nitro verification from 400M gas down to under 70M, split across two
transactions because Ethereum's block limit is 60M. Fusaka's EIP-7883 repriced `MODEXP` upward and
made it worse; Base's own verifier README says the fully on-chain flow "no longer fits in a block"
and now passes off-chain-computed modular inverses as calldata hints. By contrast Intel TDX/SGX DCAP
quotes verify on chain via Automata at roughly 4M to 5M gas, or 493k with an SP1 Groth16 wrapper,
audited and deployed across 19 networks.

**Hosted options that ship today.** Phala Cloud (Intel TDX, docker-compose, `@phala/dstack-sdk`
0.5.8, `getQuote(reportData)` capped at 64 bytes, RTMR3 pins the compose hash) at **$0.06/hr for
tdx.small**, which is cheaper than the cheapest enclave-capable EC2 instance (`c6g.large`,
$0.068/hr). Marlin Oyster (Nitro, best-documented in-TEE TLS story, pricing operator-set and not
published). Oasis ROFL ships but has no endpoint returning a raw quote with your own report data, so
a third party cannot be handed a self-contained artifact. Fleek's TEE product no longer exists; the
elizaOS TEE plugin is four minor versions behind and only ever wrapped Phala's SDK.

**Also worth knowing, and cheaper:** AWS NitroTPM "Attestable AMIs" produce the same CBOR/COSE
document with the same `--user-data` / `--nonce` binding, on ordinary networking with no vsock proxy
and no EIF build, on instance families Nitro Enclaves excludes outright (T3, T4g). It attests the
boot chain rather than a runtime-isolated enclave, so the guarantee is weaker, but for a small Node
service it is a materially simpler path.

**Verdict for Quiver.** Works technically. Converts trust-in-Quiver into trust-in-a-vendor whose
attestation key has been extracted for under $1000 on one generation and forged for under $50 on
current patched hardware. On-chain verification is practical for TDX and impractical for Nitro. Cost
is about $45/month flat regardless of call volume, which is the one genuinely attractive property.

**Latency: not measured, and I am not going to invent it.** There is no published AWS benchmark for
`NSM_GetAttestationDoc`. A figure of "47.81 ms p50" circulates attributed to arXiv 2606.22560; that
paper was fetched and contains no empirical evaluation at all. Adjacent measurements (vsock RTT p50
80 µs on `c6i.2xlarge`; enclave-to-host RTT 700 to 900 µs) disagree by 10x. Single-digit milliseconds
is plausible and is an estimate.

**One operational trap that would bite this design specifically.** A Nitro attestation certificate
expires **three hours** after issue, and the enclave clock is never resynchronised after boot,
drifting about 1 s/day and up to 7 s across a week. Evervault hit production failures from exactly
this. An observation envelope that is meant to be checkable next month cannot rest on a 3-hour
artifact without deciding, explicitly, that it accepts expired end-entity certificates, which throws
away revocation and freshness.

### 3.3 zkTLS

I expected to rule this out on ciphersuite grounds and **the measurement refuted me**, which is worth
recording because the wrong version nearly reached this page.

TLSNotary's source (`crates/tls/core/src/suites/mod.rs`, `ALL_CIPHER_SUITES`, verified at the
`v0.1.0-alpha.15` tag) compiles in exactly two suites, both TLS 1.2, both AES-128-GCM; everything
else including all three TLS 1.3 suites is commented out. Every one of Quiver's thirteen upstream
hosts negotiates TLS 1.3 by default. That looked like a clean structural kill. So I forced
`minVersion = maxVersion = TLSv1.2` with the cipher list restricted to exactly those two suites:

**All 13 of 13 hosts accepted the connection.** Hyperliquid, dYdX, Deribit, DefiLlama, all three
Polymarket hosts, both OKX hosts, and all four EVM RPCs. TLSNotary is not ruled out by protocol
compatibility.

What rules it out is everything else.

**Trust model.** The attestation is a signature over a commitment. A malicious notary can
unilaterally sign an arbitrary transcript, and prover-plus-notary collusion forges anything.
TLSNotary states it themselves: "A notary is just a verifier you didn't run yourself", and zkTLS
proofs are designated-verifier, so a contract "cannot re-witness the session". Every shipping vendor
I checked verifies on chain with `ecrecover` against an allowlisted attestor set: Reclaim
(`Claims.sol`, ecrecover per witness), Primus (`require(signatures.length == 1)`, one ecrecover
against an allowlist), zkP2P (M-of-N ECDSA). **Not one verifies a TLS session or a SNARK on chain.**
On-chain verification is cheap precisely because the chain is checking a trusted signer.

**Maturity.** TLSNotary's README says it "should not be used in production". Since alpha.13 it ships
**no notary at all**; `notary-server` and `notary-client` were removed and `notary.pse.dev` shut
down, with the crate explicitly frozen: it "will not receive new features". You would operate the
notary yourself, on feature-frozen code, and then you are the trusted party again, which is where
Quiver started.

**Bandwidth against Quiver's actual payloads.** TLSNotary's own FAQ gives roughly 25 MB fixed per
session plus about 40 KB per 1 KB of incoming data. Applied to the measured sizes:

| call | bytes | implied TLSNotary bandwidth |
|---|---|---|
| hyperliquid `metaAndAssetCtxs` | 72 KB | ~28 MB |
| deribit BTC option chain | 373 KB | ~40 MB |
| polymarket gamma limit=150 | 807 KB | ~57 MB |
| defillama `/protocols` | 8.5 MB | **~364 MB** |
| defillama `/protocol/aave` | 10.2 MB | **~432 MB** |

zkPass publishes near-identical figures for their own MPC mode and calls a 100 KB response
"impractical for regular use", which is why they default to a proxy. Two independent sources agreeing
on the order of magnitude is good evidence. Note the published latency benchmarks show full-reveal
MPC flat at about 14.5 s from 1 KB to 51 KB, which is in tension with the FAQ's bandwidth model; I
could not reconcile them and **nobody has published a benchmark past 51 KB**. Seven of Quiver's
thirteen calls are larger than any measurement that exists.

**The industry already voted.** zkP2P/Peer settled real money on Base with proxy-based zkTLS, then
replaced it with an AWS Nitro Enclave in V3, citing thirty seconds down to under one. Reclaim,
Pluto, Opacity and Clique are TEE-based or building a TEE track. Reclaim's own security FAQ: "The
only protection against fake proofs here is decentralisation or self-hosting of the attestor.
Otherwise, we must trust the Attestor."

**Two practical hazards on top.** A TLSNotary ClientHello advertising two suites and max version 1.2
is a JA3/JA4 fingerprint no real browser produces, and eleven of the thirteen hosts sit behind
Cloudflare or CloudFront, which fingerprint on exactly that. Proxy mode originates from datacenter
IPs, which those CDNs pre-flag. Neither is fatal, both are unmeasured, and I found no vendor
documentation addressing either.

**Verdict.** Not blocked on protocol. Blocked on a trusted notary you must operate yourself, on
maturity, and on payload sizes seven of thirteen of which exceed anything ever benchmarked. Pricing
where published is $0.10 to $1.00 per proof, against $0.06/hr flat for a TEE, so for a
continuously-polled risk API the economics are two to four orders of magnitude apart.

### 3.4 Oracle networks

The question is not whether oracles sign. They do. It is whether any of them signs **the quantities
Quiver actually consumes.**

| quantity Quiver reads | signed oracle substitute? |
|---|---|
| Hyperliquid perp **mark** for an asset | **no** |
| Hyperliquid hourly **funding** | **no** |
| Hyperliquid **maxLeverage** / margin tiers | **no** |
| dYdX oracle price + maintenanceMarginFraction | **no oracle, but see §4** |
| Deribit per-instrument mark IV, DVOL | **no** |
| DefiLlama protocol TVL | **no** |
| Uniswap V3 `sqrtPriceX96` / `liquidity` / `tick` | **no oracle, but provable natively, see §4** |
| Polymarket CLOB book | **no** |
| generic BTC/USD, ETH/USD spot | **yes**, abundantly |

**One of nine.** Oracle networks cover generic spot price and nothing else Quiver needs. Pyth's
3,059-feed catalogue has no funding rates, no venue-specific marks, no implied volatility, no TVL.
Chainlink's SmartData taxonomy stops at proof-of-reserve, NAV and AUM. Chainlink's DEX State Price
schema returns a derived consensus price with `bid == ask == price`, explicitly not raw pool state.
The relationship with Polymarket runs the other way: Chainlink and Pyth feed into its resolution.

Two access facts belong in any plan that leans on these. Chainlink Data Streams has **no free tier**,
from $150/month per feed, credentials HMAC. Pyth Core's unauthenticated Hermes endpoint, the one my
probe used successfully today with no key, **is being retired within weeks** and the quorum shrinks
from 13-of-19 Wormhole guardians to a 3-of-5 router set; Starter is $500/month. The two official Pyth
sources disagree on the date (docs say 2026-08-18, the blog says 2026-07-31) and I could not resolve
which is current. **RedStone's public gateway is currently the only credential-free source of
third-party-verifiable signed prices**, which makes it a dependency risk rather than a stable
assumption.

### 3.5 Multi-source consensus with divergence bounds

Cheap, requires nothing new, and has a hard floor that was measured rather than estimated. Nine
independent BTC/USD sources, four concurrent rounds:

| source | mean | vs median |
|---|---|---|
| pyth hermes | 63,433.22 | -0.027% |
| coinbase spot | 63,433.23 | -0.027% |
| deribit index | 63,433.50 | -0.026% |
| kraken spot | 63,437.30 | -0.020% |
| dydx oraclePrice | 63,450.15 | 0.000% |
| hyperliquid mark | 63,479.28 | +0.046% |
| okx spot | 63,500.40 | +0.079% |
| hyperliquid oracle | 63,501.50 | +0.081% |
| binance spot | 63,502.01 | +0.082% |

**Full spread 10.8 bps.** A divergence gate over these sources cannot detect a fabrication smaller
than roughly that, because everything inside the band is indistinguishable from honest disagreement.
For `perp-gate` a mark error passes into distance-to-liquidation roughly 1:1, so at 20x an undetected
30 bps error is 6% of the margin buffer.

It also does not defend against the adversary that matters most here. Both the primary read and the
cross-check are unsigned HTTPS terminating at Quiver's own network edge, so a single adversary
positioned there sees both.

Worth doing. Not an attestation. Should never be called one.

### 3.6 Economic bonding, slashing, optimistic challenge windows

These do not make a wrong number right. They make lying expensive and give a counterparty recourse,
which is a different and lesser good, and it only binds Quiver rather than the venue. Opacity's
EigenLayer AVS is the honest illustration: SGX is the load-bearing assumption and slashing is only
the penalty, and the shipping product is an EIP-191 signature from an allowlisted notary gated behind
an API key.

For a service with six external payers, posting a bond large enough to make fabrication irrational
would exceed a year of revenue. Real, and premature.

## 4. What actually works: attest the input against the venue's own consensus

Two of Quiver's live sources are blockchains, and a third class of its input is chain state. That
changes the question from "can we prove a server said this" to "can we read what the venue's own
consensus committed", which is a strictly stronger statement and needs no new cryptography.

### 4.1 Hyperliquid: a contract can read the mark price

HyperEVM (chain id 999) exposes read precompiles that return live HyperCore state. Measured, all
reachable from three independent RPCs:

| address | returns | measured |
|---|---|---|
| `0x…0806` | `markPx(perpIndex)` | 32 B |
| `0x…0807` | `oraclePx(perpIndex)` | 32 B |
| `0x…080a` | `perpAssetInfo(perpIndex)` | 256 B, decodes to `{coin, marginTableId, szDecimals, maxLeverage, onlyIsolated}` |
| `0x…0800` | `position(user, perpIndex)` | 160 B |
| `0x…080e` | best bid / offer | 64 B |
| `0x…0809` | `l1BlockNumber()` | 32 B |

Cross-checked against the HTTP `/info` response the adapter actually parses, over 40 live assets:

- **worst relative mark divergence 1.215e-4** (on COMP), median 0
- **`maxLeverage` agreed exactly on 40 of 40 assets**, zero disagreements
- a control that separates disagreement from clock skew: the gap between two consecutive HTTP reads
  and the gap between an HTTP read and a concurrent precompile read have **identical distributions**
  (BTC median 0, max 1.57e-5 in both). The two sources return the same value; the residual is
  latency.

And `portfolio-gate`'s account book is covered too. `position(user, perp)` returns
`[szi, entryNtl, isolatedRawUsd, leverage, isIsolated]`. On a live 5-leg book:

| leg | HTTP `szi` | precompile word 0 | match |
|---|---|---|---|
| BTC | 2.89931 | 289931 (`× 10^szDecimals`, szDec 5) | exact |
| ETH | -23.582 | two's complement of 235820 | exact |
| SOL | -22.75 | two's complement of 2275 | exact |

Leverage matched exactly on all three. `entryPx` is recoverable as `entryNtl / szi` and agrees to
about 1e-5 (ETH: 1874.07 derived against 1874.09 reported).

**A contract can read this, not just an RPC client.** That distinction is the whole point, and I
proved it rather than assuming it, using an `eth_call` state override that plants bytecode
performing a `STATICCALL` into the precompile:

```
0x60206020602060006108065afa5060206020f3
```

It returned 633620, byte-identical to the direct read, meaning BTC mark 63,362. **Cost: 3,285 gas**
above an identical-calldata no-op, at a HyperEVM gas price of 0.124 gwei.

**What is not there.** No funding precompile exists. I scanned `0x800` through `0x830` and matched
every returned word against the live funding rate (0.0000125) and open interest at six scale factors;
nothing matched. The notional **margin tier table** is also absent: `perpAssetInfo` gives
`marginTableId` (56 for BTC) but no precompile returns the table, and `perp-gate` prefers tiers over
`maxLeverage` when they are available. `eth_getProof` is **not supported** on HyperEVM (`Method not
found`), and Hyperliquid publishes no signed header, no state root and no commit signatures anywhere,
so this value cannot be exported off HyperEVM as a proof. **Verification must happen on HyperEVM.**

### 4.2 dYdX: the inputs are Merkle-provable against a validator-signed header

dYdX v4 runs unmodified CometBFT. The gRPC query path returns data with no proof
(`proofOps=NONE`, measured). The **raw store** path returns ICS-23 proofs. I located the real key
format by decoding the neighbour leaves out of a non-existence proof, which is a trick worth keeping:
a miss names the surrounding real keys.

| key | store | result | value | proof |
|---|---|---|---|---|
| `Price:` + be4(0) | `prices` | **existence** | 8 B, exponent -5, price 6334080911 | 853 B, 2 ops |
| `LiqTier:` + be4(0) | `perpetuals` | **existence** | 25 B, `Large-Cap`, IM 20000 ppm, MF 600000 ppm | 794 B, 2 ops |

Decoded: **oracle price 63,340.80911** and **maintenance margin fraction 0.02 × 0.60 = 0.012**.

The unsigned indexer response Quiver actually reads, fetched at the same time, says
`oraclePrice: 63340.80911` and `maintenanceMarginFraction: "0.012"`. **Both exact.**

The proof ops are `ics23:iavl` then `ics23:simple`, rooting the leaf into the store and the store into
`app_hash`, which sits in a CometBFT header carrying validator signatures (17 of 31 slots signed at
the height I checked, 31 validators in the set). Verifying it off chain needs an ICS-23 verifier plus
a light client. dYdX's own documentation never mentions proofs anywhere; the capability is a
byproduct of running standard CometBFT.

**What is not there.** `nextFundingRate` was not located in either store and I did not find it, so
funding is unverified for dYdX as well as Hyperliquid. And dYdX documents the hard limit explicitly:
the orderbook is in-memory per node, "not written to the blockchain or stored in the application
state", so no book depth is ever provable.

### 4.3 EVM chain state: already provable, no new mechanism

`lp-desk` and `calldata-x` read chain state. `eth_getProof` works on the free public RPCs the
adapters already use. Measured on the Uniswap V3 USDC/WETH 0.05% pool, slot 0, at a pinned block:

- account proof 8 nodes / 3,764 B, storage proof 6 nodes / 2,309 B, about 6 KB total
- 251 ms on `ethereum-rpc.publicnode.com`, 342 ms on `rpc.mevblocker.io`
- **byte-identical results from both**, which is mutual corroboration rather than a single source
- verifiable against the block header `stateRoot`

`calldata-x` already captures `blockNumber` and `blockHash` (`evmrpc.js` `getBlock`), so the anchor
is half-built. The `eth_simulateV1` result itself is not provable this way, since it is a
counterfactual execution and not committed state, but the state it ran against is.

### 4.4 Gate D0: a check that goes red

Written and run (`gateD0-input-attest.mjs`). It attests `perp-gate`'s Hyperliquid inputs by reading
the same quantities from the precompiles and refusing on divergence.

Calibration first, because a bound belongs to the gate that enforces it and never to the probe that
suggested it. Over 40 live assets: worst honest divergence **1.215e-4**, so **bound 1e-3, and the
worst honest case uses 12.2% of it**.

```
--- GREEN: honest inputs must be accepted ---
  BTC   claimed=63396.0  consensus=63396    rel=0.00e+0  maxLev ok=true  -> ACCEPT
  ETH   claimed=1872.6   consensus=1872.5   rel=5.34e-5  maxLev ok=true  -> ACCEPT
  SOL   claimed=73.0612  consensus=73.0613  rel=1.37e-6  maxLev ok=true  -> ACCEPT
  DOGE  claimed=0.069877 consensus=0.069877 rel=0.00e+0  maxLev ok=true  -> ACCEPT
  XRP   claimed=1.0491   consensus=1.04905  rel=4.77e-5  maxLev ok=true  -> ACCEPT

--- RED: fabricated inputs must be refused ---
  mark +0.5% (a plausible-looking lie)       rel=5.00e-3 -> REFUSED
  mark -5% (moves the liq price materially)  rel=5.00e-2 -> REFUSED
  mark +0.11% (just past the bound)          rel=1.10e-3 -> REFUSED
```

That transcript is one run. It was run again on fresh live data at different price levels and passed
identically (0 green failures, 0 red escapes, 0 false refusals, 118 ms), so the result is the gate
and not the market.

The tightest refusal is +0.11%, which is 11 bps. Compare §3.5: cross-venue consensus cannot see below
10.8 bps. Same-venue consensus attestation is roughly an order of magnitude tighter than cross-venue
agreement, because it compares against the venue's own committed state rather than against other
venues' opinions of the same asset.

**What this run is and is not.** As executed, the gate reads the precompile over a public HyperEVM
RPC, which is itself unsigned HTTPS. That version is multi-source consensus with a much better second
source, not an attestation, and one adversary at Quiver's network edge still sees both reads. The
attestation version is the same comparison performed **inside a verifier contract on HyperEVM**,
where the precompile value comes from consensus and not from a wire. That is the thing to build, and
the off-chain gate is the honest first half of it: it establishes that the comparison holds on live
data before anyone writes Solidity.

## 5. The hard cases, stated plainly

These have no clean answer and I did not find one.

| source | services | why nothing works |
|---|---|---|
| **Deribit** | `options-desk` | Not a chain. No signature, and no field in the response envelope where one could go. No oracle publishes per-instrument mark IV or DVOL. The option chain is 373 KB DECODED but **37,377 bytes on the wire** under gzip, measured with curl on 28 Jul 2026, and HTTP compresses before TLS encrypts. The "7x past any published zkTLS benchmark" claim is RETRACTED: size is not the binding constraint. What remains is the semantic objection. A TEE attests the fetch and not the truth. |
| **DefiLlama** | `protocol-pulse` | Not a chain. `/protocol/aave` is 10.2 MB, and TVL is a **derived, methodology-dependent aggregate**, so even a perfect proof of transport would prove DefiLlama said it, never that it is right. Two protocols can disagree on the same TVL legitimately. |
| **Polymarket** | `poly-fill`, `poly-desk`, `updown-pulse` | Order book state is off-chain by design. The `hash` field has no signer. Resolution is on chain; the book is not. |
| **OKX Web3 DEX (keyed)** | `tape-pulse`, `token-scan`, `wallet-audit`, `loop-digest`, `chart-press` | Worst case. Unsigned, **and** the buyer cannot re-fetch without their own HMAC credentials, so even the weak "go look yourself" fallback is unavailable. |
| **funding rates, both venues** | `perp-gate` | Not on chain at Hyperliquid (scanned `0x800`-`0x830`, no match), not located in dYdX's stores. Genuinely open. |
| **Hyperliquid margin tiers** | `perp-gate`, `portfolio-gate` | `marginTableId` is exposed, the table is not. `maxLeverage` is a usable but coarser substitute, and the engine prefers tiers when it has them. |

For the first four rows the honest position is that **no mechanism available today makes the input
verifiable**, and the only defensible move is to state that in the envelope rather than to attach
cryptography that implies otherwise.

## 6. What would have to be built

**Minimum viable version, and it is small.** A `QuiverPerpInputAttestor` contract on HyperEVM (chain
999) with one function:

```
function attest(uint32 perpIndex, uint64 claimedMarkScaled, uint8 claimedMaxLeverage,
                uint64 boundPpm) external view returns (bool)
```

It `STATICCALL`s `0x…0806` and `0x…080a`, decodes `szDecimals` to align the scale, and compares. That
is roughly 3,285 gas plus decode. Paired with the existing Plonk liquidation verifier it gives, for
the first time, a single on-chain transaction that checks both **that the arithmetic is right** and
**that the mark price it consumed is the one Hyperliquid's own state holds**.

The dYdX half is more work and needs no new trust: an ICS-23 verifier plus a CometBFT light client,
either off chain in the SDK or on chain. Roughly 800 to 1,900 bytes of proof per value. Existing
implementations exist in the IBC ecosystem and would be ported, not invented.

**The gates, each of which must be able to go red.**

1. **D0 (built, passes).** Off-chain cross-read with a calibrated bound, green half and red half, plus
   a control proving the bound does not reject honest latency. Extend the calibration from 40 assets
   to the full 232 and re-derive the bound from that.
2. **D1.** The Solidity attestor compiled and run in an in-process EVM against a forked HyperEVM
   state: accept the honest mark, refuse each of five tampered variants, report accept gas and reject
   gas. This is the `gateB*2` shape already used for the circuit verifiers.
3. **D2.** A scripted revert on the `gateA-revert` model: delete the attestor call, require the gate
   to go red, restore it, require green. Both halves, because a gate red in both states is broken
   rather than strict.
4. **D3.** dYdX: fetch the ICS-23 proof, verify it against `app_hash`, verify `app_hash` against the
   commit signatures, and refuse a proof taken from a different height. The last clause is the one
   that can actually fail.
5. **D4, the one that matters most.** A **negative** gate: assert that services with no attestation
   path (`options-desk`, `protocol-pulse`, `poly-*`, the keyed OKX five) do **not** claim one. If a
   future edit attaches an attestation field to a Deribit answer, this goes red. The failure mode
   this project keeps catching is a claim outrunning what was built, and this is the gate that catches
   it in the input layer.

**What must not be built.** A TEE-attested fetch for Deribit or DefiLlama. It would produce an
impressive artifact that proves the enclave received those bytes and says nothing about whether the
IV surface or the TVL number is right, on sources where that is the entire question. That is the
theatre the roadmap's abandon condition was written to prevent, and it would be the most tempting
thing to ship because it is the most visible.

## 7. Ranking

**(a) Shippable in weeks**

- **Hyperliquid precompile attestation for `perp-gate` and `portfolio-gate`.** Gate D0 already passes.
  Remaining work is the Solidity attestor, gates D1 and D2, and wiring the attestation into the
  observation envelope. Covers mark price, oracle price, `maxLeverage`, and per-leg size/entry/leverage.
  Does not cover funding or margin tiers.
- **`eth_getProof` anchoring for `lp-desk` and `calldata-x`.** About 6 KB per pool, works on the free
  RPCs already in use, and `calldata-x` already records the block anchor.
- **Multi-source divergence disclosure everywhere it is cheap.** Not an attestation, and must be
  labelled as a 10.8 bps floor, but it is honest and nearly free.
- **Gate D4, the negative gate.** Days, not weeks, and it is the highest ratio of protection to effort
  in this document.

**(b) Months**

- **dYdX ICS-23 plus light-client verification.** No research risk, real engineering: proof
  verification, header verification, validator set tracking, and the unsolved question of where the
  verifier lives given the current T2 verifier is on X Layer and this evidence is on a Cosmos chain.
- **A TDX-hosted attested fetch for the keyed OKX subset**, on Phala at about $45/month, verified on
  chain via Automata at 4M to 5M gas or 493k with an SP1 wrapper. Only worth it because those five
  services have no "go look yourself" path at all. It attests the fetch, never the truth, and the
  envelope must say so.

**(c) Needs novel research**

- **Funding rates.** Not on chain at either venue. Either the venues expose them, or somebody proves
  the funding computation from its constituent on-chain inputs, which for Hyperliquid means the
  validator oracle median and is not obviously reachable.
- **Anything that would make a derived aggregate like DefiLlama TVL verifiable.** The obstacle is not
  transport, it is that the quantity is methodology-dependent. This is arguably not a cryptography
  problem at all.
- **Publicly verifiable zkTLS.** eprint 2026/277 names the gap: existing DCTLS protocols "rely on
  designated verifiers, which prevents public verifiability and enables prover-verifier collusion in
  on-chain settings." Somebody may close it. Nobody has.

**(d) Structurally impossible**

Only one thing, and it is worth being precise because everything else above is merely unbuilt.

**No mechanism can prove a venue's self-reported number is true.** Signatures, enclaves, TLS proofs
and consensus reads all establish provenance: that this party asserted this value. Truth about an
off-chain fact is not recoverable from provenance, at any cost, by any construction. TLSNotary says
it in one line: "the TLSNotary protocol does not solve the Oracle Problem."

The consensus-state approach in §4 is the strongest available answer precisely because it collapses
the gap rather than closing it: for a venue that **is** a blockchain, the venue's self-report and the
venue's committed state are the same object, so "did Hyperliquid really say 63,396" becomes
answerable. It does not make Hyperliquid's mark price a true statement about the world, and no
version of it ever will.

## What none of this would ever prove

**Attestation is not correctness.** Gate D0 confirms that the mark price Quiver used is the one
HyperCore holds. If HyperCore's oracle is manipulated, the attestation certifies the manipulated
number with full cryptographic force. Hyperliquid's mark derives from a stake-weighted median across
Binance, OKX, Bybit, Kraken, Kucoin, Gate and MEXC, and no signed record of any validator's
submission is retrievable. The attestation reaches the venue's state and stops there.

**It does not cover the whole input, even where it works best.** For `perp-gate` on Hyperliquid it
covers mark, oracle price and `maxLeverage`. Funding is unattested. Margin tiers are unattested, and
the engine prefers tiers when present, so **the attested path may be certifying a coarser
maintenance-margin source than the one that actually produced the answer**. That is a real gap and it
would need either a tier-mode refusal or an explicit disclosure per response. It is exactly the shape
of defect this project has caught four times: a guarantee stated over the general case that holds
only over a subset.

**It covers 2 of 22 services, partially.** Adding EVM state proofs reaches 4. Of the other eighteen,
**eight need no attestation at all** (the seven proof-only engines, whose inputs the caller supplied,
plus `macro-sentry`, which reads nothing), and **ten have no mechanism**: `options-desk`,
`protocol-pulse`, `poly-fill`, `poly-desk`, `updown-pulse`, `chart-press`, `tape-pulse`,
`token-scan`, `wallet-audit`, `loop-digest`. So the honest ceiling for Phase D as scoped here is
**4 of the 14 services that contact an external host**, and the remaining ten are §5.

**The off-chain version of D0 is not an attestation.** Until the comparison runs inside a contract on
HyperEVM, both reads are unsigned HTTPS to the same host, and one adversary at the network edge
defeats both. The gate as it stands proves the two sources agree; it does not remove Quiver from the
trust path.

**A signed observation still says nothing about whether the number should have been believed.** The
T1 signature binds a hash to a key. Attesting the input binds the input to the venue. Neither speaks
to model risk, to whether the venue's mark was stale during a wick, or to whether a liquidation price
computed from an honest mark was the right thing to act on. `portfolio-gate` already cross-checks the
venue's own `liquidationPx`, which is a better instrument for that question than anything in this
document.

## 8. Build notes: the dYdX half of input attestation, implemented

Section 4.2 above is research and is left as written. This section records what happened when it was
built, including the place where the research turned out to be right and an intermediate
implementation turned out to be wrong.

**Files.** `veritape/src/adapters/ics23.js` (ICS-23 + a minimal protobuf reader, venue-agnostic),
`veritape/src/adapters/dydx-attest.js` (the dYdX attestation and light-client checks),
`veritape/gates/gateD3-dydx-input-attestation.mjs`, `veritape/gates/gateD3-revert.mjs`. Mirrored into
`Quiver/` at the same relative paths. Nothing was deployed, nothing went on chain, and
`src/engine/` was not touched — the published build hash is `q1-e1fa99d08887d6cc` before and after,
in both trees.

    npm run gate:d3            # 9 tests, ~11 s, live against dYdX mainnet
    npm run gate:d3-revert     # injects 4 defects, requires RED each time, then GREEN

### 8.1 The trust chain, precisely

Seven checks, all recomputed locally: `ics23:iavl` leaf to store root, `ics23:simple` store root to
`app_hash`, `app_hash` equals the header field at H+1, the header's 14-field Merkle hash equals
`commit.block_id.hash`, the validator set hashes to `header.validators_hash`, **every precommit
ed25519-verifies and the verified voting power exceeds 2/3**, and all of it is repeated against three
independently operated RPC providers that must agree on chain id, block hash and `app_hash`.

The honest one-line claim is therefore: *this value is in dYdX's state tree under an `app_hash` bound
into a block that more than 2/3 of the voting power of the validator set named by that block signed
for, and three independent providers report the same block.*

**What is still missing, and it is not cosmetic.** There is no trusted checkpoint. The validator set
comes from the same RPC and is checked against `validators_hash` in the header that same RPC served —
internally consistent but circular. A provider could invent a validator set of its own keys, sign a
fabricated block with them, and all seven checks would pass. Only corroboration stands in the way, so
the attack needs collusion across three separately operated providers rather than one lying node.
Closing it properly needs a weak-subjectivity checkpoint pinned out of band, which is not built. The
module has a `TRUST.CHECKPOINTED` label that is deliberately never returned, and the gate asserts it
is never returned. Freshness is also unattested: honest providers can still withhold, delay, or
choose which recent height to serve.

### 8.2 The signature encoder: 4.2's title was right, an intermediate build called it wrong

An intermediate version of `dydx-attest.js` contained a signature checker that verified **zero**
signatures, on dYdX and on ten other CometBFT chains, and concluded from that breadth that the defect
was unreachable and no light client was possible. It documented the negative result carefully and
downgraded the trust label to match. That conclusion was wrong, and the breadth of the failure was
the thing that made it look credible — failing identically everywhere reads as a property of the
chains rather than a bug at home.

The defect: CometBFT `CanonicalVote` is proto3, and proto3 **omits a scalar field whose value is the
type default**. `round` is 0 in the overwhelming majority of blocks, so the correct sign bytes contain
no `round` field at all. The old encoder wrote an explicit zero `round` (tag `0x19` plus eight zero
bytes), producing bytes nobody ever signed.

It was found by search rather than by reasoning: 432 candidate encodings over 7 axes were generated
and tested against real precommits, and **exactly one verified**. Emitting `round` only when non-zero
is the whole fix. Measured after it: **0 signature failures** at five heights spanning 50,000 blocks
(about 18 h), 89-95% of voting power verified, **identical results from all three providers**. Two
controls were run first, because a verifier that cannot fail proves nothing — a self-generated
ed25519 signature verifies through the same raw-key path, and every tamper mutation (block hash,
parts hash, height, chain id, timestamp, round) drops verification to 0 of 25.

So 4.2's title, "provable against a validator-signed header", is correct. What 4.2 reports as
"17 of 31 slots signed" is a count of *slots*, not of verified signatures; slot counts are not
evidence until the signatures verify, and now they do.

### 8.3 The measured divergence, and the bound

2,958 market-observations (296 markets x 10 rounds, three sweeps, ~15 min window), each comparing the
live indexer against a signature-verified proof at the anchored height. Zero proof errors.

| quantity | exact matches | worst divergence | bound | worst honest case uses |
|---|---|---|---|---|
| `maintenanceMarginRate` | **2958 / 2958** | **0** | 1e-12 | **0.0%** |
| `initialMarginRate` | **2958 / 2958** | **0** | 1e-12 | **0.0%** |
| `oraclePrice` | 99.04% (of 1776) | 3.121e-3 (AVAX-USD) | 1e-2 | **31.2%** |

The oracle divergence is **not continuous drift**. dYdX posts oracle updates in discrete steps, so a
market either has not moved since the anchored height (exact match) or has taken one update step
inside the ~5 s gap between the anchored block and the indexer read. p99.9 was 1.118e-3. The bound of
1e-2 is about 3.2x the worst of 2,958, chosen so ordinary steps do not false-refuse.

**The cost of that bound, stated plainly: an indexer misreporting a price by less than 1% is not
caught.** That slack is bought by the timing gap and cannot be closed by tightening the number — only
by shrinking the gap. The static margin parameters have no such slack, because both sides are exact
decimals derived from the same integer ppm fields; a lie of any size above 1e-12 relative is caught
there. That asymmetry is the honest summary of what dYdX input attestation is worth today.

The sample is one ~15-minute window on one day in a calm market. A volatile regime would widen the
oracle tail and the bound would need re-deriving. It is a measurement, not a constant.

Cost: three proofs per market (`Perp:` then `Price:` and `LiqTier:`), 2,259-2,523 bytes total,
individually 853 B for price and 794 B for the liquidity tier — matching 4.2's recorded sizes exactly.

### 8.4 What is refused, on purpose

`fundingHourly` is **not attestable** and the module says so by name rather than omitting it. The
perpetuals store holds `PremSamples`/`PremVotes` and a cumulative `funding_index`; the hourly rate the
indexer publishes is computed at the hour boundary and never committed under a key. This confirms
4.2 — and it is a live gap, because `perp-gate` consumes that value. Orderbook depth is refused for
the reason 4.2 gives: dYdX documents it as in-memory per node. An unregistered quantity is refused as
`UNKNOWN_QUANTITY`, a missing bound as `NO_BOUND`. There is deliberately no "probably fine" branch.

### 8.5 Corrections to 4.2 from building it

1. The perpetuals key prefix is **`Perp:`**, not `Perpetual:`. `Perpetual:` + be4(0) returns a
   non-existence proof on mainnet. 4.2 never queried it, so the doc does not state it wrongly, but
   anything built from its naming would miss. The neighbour-decoding trick 4.2 describes is exactly
   what recovered it.
2. 4.2 attests maintenance margin by reading `LiqTier:` + be4(0) directly. That is only correct for
   markets that happen to use liquidity tier 0. The market-to-tier mapping lives in the `Perpetual`,
   so a correct attestation needs **three** proofs, not one. Four tiers are live (Large-Cap,
   Small-Cap, Long-Tail, Isolated).
3. `clobPairId` to `perpetualId` is an assumption, so it is verified rather than trusted: the
   on-chain ticker must equal the ticker asked about, and the attestation is refused otherwise.
   Without that check the failure mode is attesting BTC's price against ETH's proof, which is worse
   than none.
4. "Verifying it off chain needs an ICS-23 verifier plus a light client" — both are now built, in
   about 780 lines with no new dependencies.

### 8.6 The gate can fail, and this was executed

`npm run gate:d3-revert` removes one load-bearing check at a time and requires the gate to go red:

| defect injected | result |
|---|---|
| proto3 zero-omission in the vote encoder (the historical defect) | 1 pass, **8 fail** |
| the divergence comparison (`rel <= bound` becomes `true`) | 6 pass, **3 fail** |
| the no-proof-path refusal | 8 pass, **1 fail** |
| the ticker cross-check | 8 pass, **1 fail** |
| **all restored** | **9 pass, 0 fail** |

The gate includes the knife-edge case that catches a comparison which has quietly stopped comparing: a
value **marginally past** the bound must be refused, and one **marginally inside** it must still
attest. Both assert their own construction landed on the intended side before trusting the verdict.

**Thin evidence, said plainly.** The divergence bound rests on one calm ~15-minute window. Signature
verification is confirmed over 50,000 blocks on one chain on one day. The absence of `nextFundingRate`
in the stores remains *not found* rather than *not there*. And the whole light client is one trusted
checkpoint short of standing on its own without provider corroboration.

### 9.2 Funding: verified absent, not repeated from a doc

returned 32-byte words and matched each against the live hourly funding of **10 assets chosen for
distinct funding values** — a match against a rate every asset shares would prove nothing — at every
power of ten from 1e-18 to 1e18, both sign conventions, both two's-complement readings. **104,932
candidate scalings. Zero matches.**

Funding is not available on Hyperliquid, confirming 4.1's conclusion by a wider method. One
refinement: what a single-shape scan misses is **calldata shape, not address range**. `0x800`,
`0x801`, `0x80f` and `0x813` answer only an address+index shape and look dead to a scan sending a
bare `uint32`. Sweeping to `0x8ff` also establishes the negative — nothing above `0x814` answers
anything.

### 9.3 The bound — and 4.4's flat 1e-3 does not survive the full universe

`/info` is a snapshot, not a live read: **60 polls over 23.0 s produced 59 distinct snapshots**,
turning over every ~388 ms median (min 295, max 853 — and the max is bounded below by the ~380 ms
poll interval, so it is an upper estimate). The residual against the precompile is therefore snapshot
staleness. So the HTTP value is **bracketed** between two consensus reads rather than compared to one.

Calibration: **26 rounds × 232 assets = 6,032 observations.**

| | |
|---|---|
| inside the raw bracket with **no allowance at all** | 5,621 of 6,032 (**93.2%**) |
| p99 / p99.9 / max relative residual, bracketed | 1.692e-4 / 3.436e-4 / **1.131e-3** |
| max relative residual, **flat** (unbracketed) comparison | **5.956e-3** |
| max residual in ticks | 500 |

**The bound is two-term: `allow = 5e-4 · price + 2 · tick`. Worst honest observation uses 58.1% of it;
0 of 6,032 breached; 0 of 26 rounds would have turned the gate red.**

Two terms because the residual has two unrelated causes, and this is the finding that breaks 4.4:

- The worst **relative** residual, 1.131e-3 on **W**, is **exactly one tick**. W trades near 0.0088
  on a 1e-5 grid, so one unavoidable step of price-grid quantisation is 1.1e-3 of its price.
- The worst residual **in ticks**, 500 on **ZEC**, is only 1.077e-4 relative — a 1e-4 grid against a
  464 price.

Neither term alone covers both regimes. **§4.4's flat 1e-3 bound is breached by honest data: W uses
113.1% of it.** The 40-asset sample 4.4 calibrated on contained no sub-cent asset, so it never saw
the quantisation regime — which is why it reported the worst case using 12.2% of the bound and was
wrong about where the worst case even lives. A purely relative bound wide enough to admit W needs
at least 1.2e-3, **looser than the 10.8 bps cross-venue consensus floor of §3.5** — so a flat bound
does not merely lose precision, it loses the argument for doing this at all. The gate asserts
`bound.rel < 10.8e-4` so that can never be quietly given back.

### 9.4 A contract can read it, and what it costs

Reproduced 4.1's central claim: planted bytecode `STATICCALL`ing `0x…0806` returns **byte-identical**
output to the direct read (`eth_call` with a state override — a simulation; nothing deployed).

4.1's **3,285 gas** and an intermediate build's 3,272 are both single-shot figures that fold in their
own baseline, and the binary-search one is additionally inflated by EIP-150's 63/64 rule. Differencing
*N* against *N−1* copies of the same read holds the transaction base, surrounding opcodes and memory
expansion constant:

| N | 1 | 2 | 3 | 4 | 5 | 6 |
|---|---|---|---|---|---|---|
| gas | 24,582 | 27,819 | 31,057 | 34,294 | 37,531 | 40,769 |
| marginal | | +3,237 | +3,238 | +3,237 | +3,237 | +3,238 |

**3,237 gas per additional read** (3,218 for the `STATICCALL` and precompile alone, less the 19 gas of
`PUSH`/`GAS`/`POP` around it). Perfectly linear, and **the N=1→2 step equals the steady-state step to
within 1 gas — the precompile is already warm on first touch, so there is no 2,600-gas cold-account
surcharge.** Gas price measured 0.1 gwei (4.1 saw 0.124; it is a market quantity).

### 9.5 A gap found in the adapter's own guarantee

The adapter documented the HTTP value as sitting *between* the two consensus reads, but its API took
the claim as a parameter and **could not verify when it had been fetched**. A claim fetched before the
first consensus read is older than both, and no allowance legitimately brackets it — so the documented
guarantee had a hole the code could not close. Fixed: `fetchClaimed` lets the adapter fetch the claim
itself inside the window, `claimedAt` lets a caller prove the timing, and with neither the result
reports `straddled: null` and `bracketValid: false`. Unknown is reported as unknown.

### 9.6 The gate can fail, and this was executed

`npm run gate:d-hl-revert` removes one load-bearing check at a time and requires the gate to go red:

| defect injected | result |
|---|---|
| baseline, unmodified | **19 pass, 0 fail** |
| the bound is not enforced (`compareToBracket` can never say DISAGREE) | 13 pass, **6 fail** |
| the perpIndex is not confirmed on chain | 18 pass, **1 fail** |
| **all restored** | **19 pass, 0 fail** |

Both halves are asserted, not just the red one: a gate red in *both* states is simply broken and would
satisfy a one-sided check. The gate carries the knife edge — a value **2% past** the allowance must be
refused while one **2% inside** it must attest, asserted on the pure comparison core offline so a
moving market cannot excuse it — plus live fabrications, a live overshoot computed from the live
bracket, a misaligned index that must produce a *refusal* rather than a divergence number, and a dead
RPC that must yield `UNAVAILABLE` rather than a pass.

### 9.7 What this does not prove

**Green here is not an attestation.** Both reads are unsigned HTTPS from one host, so one adversary at
the network edge sees both. It is multi-source agreement with a much better second source —
HyperCore's own consensus state — and it becomes an attestation only when the comparison runs *inside*
a contract on HyperEVM. That a contract can do it is measured; that it *does* is not built. And 4.1's
finding stands: `eth_getProof` is unsupported and Hyperliquid publishes no signed header, so this
cannot be exported off HyperEVM as a proof.

**Nor does agreement mean the number is right.** Hyperliquid's mark is a stake-weighted median of
external venues; a manipulated oracle would be attested with full force. Attestation reaches the
venue's state and stops there.

**Thin evidence, said plainly.** 6,032 observations is one host, on one day, over roughly 25 minutes
of a calm market — the bound's 58.1% worst case has 1.7× headroom against *that* window and no claim
is made about a volatile one. This gate is a live-market measurement and a genuine spike can turn it
red; the bound is not padded to prevent that. Funding remains **not found** rather than proven absent:
104,932 scalings failing to match is strong, but it is a search, not a proof of non-existence.
`marginTiers` is unattested and 36 assets actually use it. And the position path (`0x…0800`) is
decoded and exercised but was **not** re-verified against a live multi-leg book in this build — 4.1's
5-leg check is the only evidence for it, and it is not mine.
